# v2.8.1：恢复用户维护目录

用户明确要求撤销此前擅改的分类，并禁止未经允许修改其手动维护或确认的内容。此次授权仅用于恢复与保护，不再重新设计分类。

## 恢复依据与边界

- 基准：Git 提交 `3e077cd` 中用户维护的 `catalog.js`。完整恢复 14 个一级目录、79 个二级菜单以及原有 231 条定义的名称、顺序、归属和字段。
- 自动测试对上述完整目录和定义计算 SHA-256，与该历史版本逐字序列化结果核对；不是只核对条数。
- 保留旧配方已引用的 6 条兼容定义，避免破坏稳定 ID。这些程序补充记录不混入原目录；若用户已修改或在其下维护内容，仍可访问。
- 一级入口不再提升“液体材料／固体材料”的下级，也不再用界面文案替换维护名称。树按照实际 `parentId` 展示，不把标签关系擅自变成目录关系。
- 仅凭 `customized: false` 不能覆盖已有分类或配方。已有内容、删除和后续编辑受到保护；只有明确执行的编辑、导入或本次指定恢复才改写。

## 已受影响设备的恢复

`catalog-recovery.js` 记录公开 Git 历史中 `8aca789`、`ec9ff25`、`d914d76` 造成的 53 组已知变化。启动时先保存 `backup-before-v2.8.1-catalog-restore` 快照，仅在整条定义与已知错误记录完全一致、且未标为手动编辑时恢复。任何额外修改都跳过；恢复标记防止下一次刷新重复执行。

该过程不整库回滚，不删除后续新增库存、配方或自建分类，不修改配方源数据及选项。原有特基拉、苏格兰和朗姆的配方匹配兼容规则在匹配时计算，不重写用户目录来实现匹配。
